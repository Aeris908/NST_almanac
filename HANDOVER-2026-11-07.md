# Передача проекта другому агенту — 2026-11-07

**Для агента, который продолжает работу:** этот файл — полный контекст. Читать вместе с
`README.md` (он объясняет *почему* так устроено сборка и данные; здесь — *как работать*).
HEAD на момент написания: `7471e6c`, дерево чистое, 214 тестов, 23 инварианта, гейт 22/22.

**Цель проекта:** архив-витрина киберспортивного сообщества NST (Nekketsu Soccer League, Goal 3 /
Goal 4) — девять сезонов плюс кубковые, клубные, командные, сольные и молодёжные турниры, с
рейтингом Elo, историей игроков и встроенной панелью правки, которой пользуется владелец.

**Архитектура в одну строку:** файлы-носители и живая выгрузка → единая SQLite-база
`data/nst.db` → из неё читают и страница, и мастер-таблица. База кормит страницу, а не наоборот.

**Стек:** Python 3.15 (без виртуального окружения, зависимости только stdlib), SQLite,
`pytest`, `ruff 0.17.3` (только проверка счётчиков), статичная витрина на HTML/JS +
Vercel-функция для правки.

## 2. Доступ, секреты, чего нельзя делать

- VK-токен берётся **только** из `VK_API_TOKEN` или `.env` (`portal/env_file.py: secret`).
  Пользовательский ключ, админства у сообщества нет. **Токен никогда не печатать и не слать в чат.**
- `.env` не должен попасть в git; в репозитории лежит только `.env.example`.
- `vercel.json` имеет `outputDirectory: "."` — всё закоммиченное отдаётся сайтом. Никаких
  секретов и временных файлов в дереве.
- Сервер правки поднимать **только** с одноразовым `NST_EDITOR_TOKEN` в окружении процесса.
- Классификатор блокирует: `vercel ls`, `npx vercel`, `taskkill //F //IM python.exe`
  (машино-широкое действие), чтение `HKCU\Environment`. **Не повторять эти попытки.**
  Локальные серверы останавливать по конкретному PID (см. `scratch/stop_static_8099.ps1`).
- Вне рабочей директории ничего не трогать. На столе есть чужая папка `Мastер-таблица`
  (латинская «М») — не удалять без слова владельца.
- Push, force-push, теги, удаление веток — только по явному просьбе.

## 4. Модель данных (коротко, без этого правки не делать)

- `matches` — один слой на строку: `row_set ∈ {pool, catalog, special, team}`; `phase`,
  `status`, `in_rating_pool`, `manual`, `duplicate_of`, `hidden_by`, `doc_id`, `tour`,
  `league`, `is_playoff`, провенанс `source`, `source_ref`, `source_locator`, `source_page`,
  `source_text`, `note`.
- `match_sides` (2 на матч: `side_index`, `outcome`, `score`, `label`) → `side_players` →
  `players` (`kind ∈ player|clan`) → `player_aliases` (`alias UNIQUE`, `source ∈
  name_tables|editor`, `ON DELETE CASCADE`).
- `tournaments(id, season, kind, name)` и `tournament_docs` — рамка спец- и командных турниров.
- `corrections` — журнал правок. **В незакоммиченном состоянии база обязана иметь пустой
  (неотменённый) журнал**, иначе падают `tests/test_refusals.py` и `tests/test_publish.py`.
  Сейчас там одна строка с `reverted_at` (откат слияния из #78) — это нормально.
- Структурные исправления делаются **воспроизимо сборкой**, а не операцией правки. Правка
  через `db/edit.py` заносит строку в журнал и ставит `manual = 1` — её нельзя использовать
  для массовых изменений.
- `hidden_by` прячет строку от витрины, `duplicate_of` только помечает (ничего не прячет).
- Elo (`portal/elo.py`): R0=1500, K = 24 лига / 32 плей-офф / 16 прочее, S = 1 / 0.75 (ОТ
  **или** буллиты) / 0.5 / 0.25 / 0, MOV-потолок 2.0. Смена счёта без смены победителя
  рейтинг не двигает; пул при этом попадает в `pool_fingerprint` мастер-таблицы.
- `data/nst.db` **не** в git (игнорируется) — он regenerable. В git попадают: носители,
  `data/vk_recheck_*.md|json`, `data/sportcup_decisions.json`, `soccer.html`, `index.html`,
  `quotes.html`, `deploy/`, `nekketsu_master_table.json`, `data/headline_stats.json`.

## 6. Как проверить любую правку

```bash
python -m pytest -q                      # 214 тестов
python db/validate.py                    # 23 инварианта
python scratch/verify_build.py check     # сам запускает build_all.py и сверяет 22 артефакта
```

- Если вывод витрины изменился **законно**: посчитать смысловой дельт-аут
  (`db/api.diff(before, after)` — позиционный diff на пересортированных списках врёт),
  открыть страницу в браузере и проверить глазами, затем `python scratch/verify_build.py snapshot`.
- Счётчики `ruff check <файл>` сравнивать для каждого тронутого файла отдельно с его же
  версией из HEAD: `git show HEAD:path | ruff check --stdin-filename path -`.
- Витрина локально: `python -m http.server 8099 --bind 127.0.0.1`, дальше
  `mcp__browser-use__navigate_page` / `evaluate_script`.
- Скриншот работает только если встроенный браузер виден пользователю; иначе проверять DOM
  через `evaluate_script` (лимит ~15 с на скрипт).

## 8. Ловушки (все измерены, не догадки)

1. `import build_final_analytics` сам проверяет соединение с VK и грузит снапшот — любой
   промер, который его импортирует, уходит в сеть. Для офлайн-промеров читать JSON напрямую.
2. Позиционный diff payload врёт на пересортированных списках — только `db/api.diff`.
3. `scratch/verify_build.py check` **пересобирает сам**; «файлы изменились до пересборки» —
   не баг, а порядок шагов.
4. id строк базы меняются от сборки к сборке: в отчёте сверки и в задачах ссылаться на id
   можно только как на «id в текущей сборке».
5. `insert or ignore` в `db/build_db.py: import_aliases` не дописывает уже существующий
   алиас — направление правки отдельно (см. `#81` прошлой итерации).
6. Пул проверять по `side_players → players.nick`, а не по `match_sides.label`: label хранит
   написание источника, и по нему проверка даёт ложный ноль.
7. `git add` с одним несуществующим путём отменяет всю команду; не глушить stderr.
8. В Git Bash `$_` и русские пути в `-Command` ломаются — скрипты правки писать файлом
   (`.ps1`) и с ASCII-сообщениями внутри.
9. Инвариант «алиас не переименовывает уже заведённого игрока» и `fold_duplicate_cards`
   держат карточки от склейки гомоглифов; менять это можно только вместе с тестом.
10. Правка в `data/sportcup_decisions.json` до уже занесённой игры сама не доходит:
    `db/build_db.py` обновляет у существующих строк только `note` и `phase` (где `manual = 0`).

### Как брать задачу в работу

Один шаг — одна задача. Список дел сразу весь, параллельные субагенты только с разделением
файлов; файл, который ведёт субагент, в полёте не трогать и не пересобирать. Каждая задача
закрывается коммитом с русским сообщением по образцу существующих («#NN: что и почему»),
после полного цикла проверки из раздела 6.
