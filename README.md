# 🏆 NST Almanac — Nekketsu Sports Tournaments Portal & Archive

Интерактивный ретро-портал, статистика, глобальный Elo-рейтинг, Зал Славы и историческая летопись киберспортивного сообщества **NST (Nekketsu Sports Tournaments)** по легендарной серии игр **Kunio-kun** (*Goal 3 / Nekketsu Soccer League*, *Nekketsu Hockey*, *Basketball*, *Kakutou Densetsu*).

Сайт выполнен в аутентичной 8-битной эстетике Famicom/Dendy с кинескопным CRT-эффектом, карточками игроков, интерактивными фильтрами, историей дуэлей (H2H) и **встроенным аудиоплеером**, который не прерывает воспроизведение чиптюнов при переходах между страницами.

---

## 🎮 Содержимое портала

1. **Главный хаб (`index.html` / `deploy/index.html`)**:
   - Интерактивный 100% экранный лаунчер в стиле меню картриджа Famicom.
   - Навигация по спортивным дисциплинам: **Goal 3 (Футбол)**, **Хоккей**, **Баскетбол 2x2**, **Файтинг**, а также переход в **Зал Цитат**.
   - Анимированные пиксельные баннеры, CRT-сканлайны, неоновый ретро-стиль.

2. **Футбольный портал Goal 3 (`soccer.html` / `deploy/soccer.html`)**:
   - **Таблицы сезонов (Сезоны 1–9+)**: регулярные чемпионаты, Высшая и Дворовая лиги, сетки плей-офф, серии пенальти, блиц-турниры и кубки.
   - **Мастер-таблица Elo**: глобальный динамический рейтинг игроков (формула в `portal/elo.py`: старт 1500, K по весу соревнования с поправкой новичка и разгрома мячей, цена овертайма и буллитов, штраф за простой).
   - **Head-to-Head (H2H)**: статистика личных встреч между любыми двумя игроками за всю историю лиги.
   - **Зал Славы (Hall of Fame)**: титулы, медали, лучшие бомбардиры и сухие матчи (с корректной фильтрацией без искажений от спецтурниров).
   - **Летопись турниров**: исторические описания, ключевые моменты и ссылки на оригинальные архивные посты ВКонтакте.

3. **Цитатник NST (`quotes.html` / `deploy/quotes.html`)**:
   - Золотой фонд цитат, локальных мемов и афоризмов игроков сообщества с 2015 года.
   - Поиск в реальном времени, фильтрация по авторам и категориям.

4. **Бесшовный 8-битный аудиоплеер (`audio-player.js`, `audio-player.css`)**:
   - Оформлен как ретро-магнитофон / кассетная дека внизу экрана.
   - Сохраняет непрерывное воспроизведение треков при переходах по страницам (встроенный PJAX-роутер).
   - Умеет переключать плейлисты в зависимости от активного раздела (музыка хаба, футбольные темы, хоккей и т.д.).

## 🚀 Быстрый запуск

### Вариант 1. Без установки (просто открыть в браузере)
Просто откройте файл `index.html` (или `deploy/index.html`) в любом современном веб-браузере (Chrome, Firefox, Edge, Opera, Safari).

### Вариант 2. Локальный веб-сервер (рекомендуется)
Для корректной работы всех AJAX-запросов и аудиоплеера рекомендуется запустить встроенный локальный сервер Python:

```bash
# В корневой папке проекта выполните:
python -m http.server 8000
```
После чего откройте в браузере: **`http://localhost:8000`** (или `http://localhost:8000/deploy/`).

## 🛠️ Сборка и обновление проекта

Вся кодовая база спроектирована так, чтобы проект можно было пересобрать в один клик.

### Сборка на Windows
Дважды кликните по файлу **`build.bat`**.

Скрипт автоматически:
1. Просканирует аудиофайлы и обновит манифесты плейлистов.
2. Синхронизирует единую базу матчей `data/nst.db` (рейтинговый пул из снапшота и рукописных блоков).
3. Импортирует в базу каталог сезонов, спец- и командные турниры из файлов-носителей.
4. Проверит целостность базы (`db/validate.py`) и остановит сборку при любом дефекте.
5. Перегенерирует мастер-таблицу `nekketsu_master_table.json` из базы.
6. Пересоберёт страницу футбола `soccer.html` — все матчи и турниры она читает из базы.
7. Пересоберёт страницу цитатника `quotes.html`.
8. Сгенерирует главную страницу `index.html`.
9. Скопирует готовую сборку для продакшена в папку `deploy/`.

### Сборка через Python (любая ОС)
```bash
python build_all.py
python build_all.py --from-store   # те же страницы из готового data/nst.db, срез не пересобирается
```

`--from-store` пропускает три шага, которые перегенерируют базу из носителей (`db/build_db.py`,
`db/import_stores.py`, `db/import_live.py`), и оставляет валидацию, мастер-таблицу и страницы.
Без базы он отказывается, а не собирает пустой сайт. Режим нужен для выката правок лороведа:
обычный прогон пересоздаёт срез заново, и защита `manual` спасает отдельные строки, но не срез —
пересобранная база уже не равна той, что отредактировали в панели.

### Токен ВКонтакте (необязательно)
Для выгрузки комментариев и видео из архива сообщества `build_final_analytics.py` читает
токен из переменной окружения `VK_API_TOKEN` (пример — `.env.example`). Без него сборка
проходит: имя группы подставляется значением по умолчанию, а запрос к API не делается.
Публичный токен в коде больше не хранится.

### Точка подключения: `db/store.py`

Все модули `db/` открывают базу через `store.connect()` и берут у него путь по умолчанию: прямого
вызова драйвера в репозитории не осталось, кроме самого `store.py`. Это шов, ради которого затеян
перенос, — серверная база подключится здесь, а не в двадцати шести местах.

С той же целью `side_players` и `player_aliases` получили собственный `id`: раньше строка журнала
адресовала их по скрытому SQLite `rowid`, которого в Postgres нет. `python db/build_db.py`
перестраивает эти две таблицы на месте при первой сборке после правки схемы и сохраняет прежние
номера строк вместе с разрывами в них, поэтому старые снимки журнала указывают на те же записи, а
`--rebuild` с потерей правок для перехода не нужен.

Там же живёт и `fold()` — регистронезависимость текста. Встроенный `lower()` в SQLite знает только
латиницу, поэтому поиск по «Дворовая лига» возвращал ноль: кириллица этим `lower()` не сворачивается
вовсе. Функция регистрируется на каждом соединении, а генератор PG-схемы заменит `fold(...)` на
`lower(...)` — тот юникод знает.

Перевод схемы и запросов на Postgres собирает `db/pg.py`: вход — текст, выход — текст, без
побочных эффектов и без второго файла схемы, за которым надо угонять. `INTEGER PRIMARY KEY`
становится `GENERATED BY DEFAULT AS IDENTITY` (не `ALWAYS`: откат вставляет id явно),
`datetime('now')` — текстом в том же формате UTC, `PRAGMA` остаётся в SQLite, `?3` — именованным
параметром `%(p3)s` (в фильтре поиска один номер используется дважды). По пути правки
`group_concat` не переводится, а убран вовсе: порядок строк в нём не обещан ни одной версией
SQLite, поэтому состав стороны и отпечаток базы собирает Python.

### Правка базы: `db/edit.py`
До появления интерфейса единственная запись в базу — этой программой. Каждое изменение пишет
в таблицу `corrections` по одной строке на поле (старое значение, новое, редактор, время) и
помечает матч `manual = 1`, после чего импортёр его не пересоздаёт.

```bash
python db/edit.py show 403
python db/edit.py set-score 403 5 1 --editor aeros   # счёт и исходы сторон пересчитываются
python db/edit.py set-place 403 --tour "5 Тур" --stage "1/4 финала"   # перенос игры
python db/edit.py set-date 403 --played-on 2024-05-01 --editor aeros  # год партии для Elo
python db/edit.py set-phase 403 --phase penalties --playoff yes       # овертайм/буллиты/плей-офф
python db/edit.py rename-player 32 "E_not" --editor aeros             # ник и адрес карточки
python db/edit.py merge-player 32 85 --editor aeros                   # #85 уходит в #32 алиасом
python db/edit.py drop-match 404 --editor aeros                       # удалить игру
python db/edit.py void 403 --reason "матч не игрался"
python db/edit.py unhide 404                          # вернуть строку, скрытую как дубль
python db/edit.py log                               # последние записи журнала, с меткой [op:…]
python db/edit.py undo last                           # откатить последнюю операцию целиком
python db/edit.py undo op:3635bbeeb105               # …или любую операцию по её метке
```

Если после правки источник настаивает на своём счёте, импортёр не спорит: ручная строка
остаётся на витрине, принесённая копия прячется за неё, а спор записывается в `incoming`
(batch `edit-conflicts_2026-11-03`) — это то самое «источники предлагают дельту, решает
редактор». Если бы этой защиты не было, правка живела бы до ближайшего импорта.

`undo` откатывает поля и снимает с матча `manual`, если действующих правок на нём не осталось:
флаг — защита строки от импортёра, а не память о прикосновении. Иначе каждая проверочная правка
навсегда выламывала бы кусок витрины из пересборки базы. `db/build_db.py --rebuild`
пересоздаёт файл, только если в журнале не осталось ни одной неотменённой записи.

### API правки: `db/api.py`
То же правописание, но одним вызовом и с ответом «что сдвинется» — это контракт для карандашей в
интерфейсе (шаг 5). Операция применяется кодом `db/edit.py` (тех же функций), затем перечитывается
payload страницы (`portal.build_soccer.compose_payload`) и наружу отдаётся **дельта**, а не 3.9 МБ
данных:

```bash
python db/api.py show 412                              # ревизия базы и строка глазами страницы
python db/api.py set-score 2928 5 1 --editor aeros     # предпросмотр: живая база не тронута
python db/api.py set-score 2928 5 1 --editor aeros --apply
python db/api.py unhide 412 --editor aeros --apply --expect cc1314c566e163e4
python db/api.py undo last --editor aeros --apply
```

- **Предпросмотр считается по копии базы** (`sqlite3.backup` во временный файл): смотреть, что
  изменится, и менять — один и тот же код, других путей пересчёта в проекте нет.
- **Форма дельты повторяет форму payload.** Лист — это `[было, стало]`; списки словарей с
  опознавательным полем (`player`, `id`, `name`) разбираются по нему, поэтому правка счёта приезжает
  как `profiles.Rock.goals_for: [148, 149]`, а не как новый массив из 92 профилей. Порядок в таких
  списках сам по себе данные (место в мастер-таблице = ранг), поэтому перестановка уезжает в
  `__order__`. Истории игроков и таблицы матчей целиком не пересылаются: изменённая строка едет в
  `match`, для игроков с изменившимися числами прикладываются конкретные сдвинувшиеся строки
  истории, а если список изменился по составу — приходит `{"__length__": [было, стало]}`.
  Правка счёта в спецтурнире — это ~1 КБ ответа, перестановка результата в пуле — ~10 КБ.
- **`expect` — оптимистичная блокировка.** Ревизия считается по содержимому (статус, скрытость,
  метка `manual`, счета сторон), а не по часам. Между предпросмотром и записью база могла измениться
  под другим редактором — в этом случае запись отклоняется с `ok: false`, а не перетирает чужую
  правку.
- **Транспорта нет намеренно.** Страница с карандашами публична, поэтому личность редактора обязана
  проверяться на сервере в каждом вызове, а `editor` обязан приходить из этой проверки, а не из
  запроса. Лицом API пока служит CLI — он печатает ровно тот JSON, который вернёт обработчик
  (Vercel Function + Neon, когда дойдёт до публикации правок).
- **`void` больше не «пустая» правка.** «Снять матч с зачёта» решено так: этой игры нет ни в
  таблицах, ни в числах, ни в истории игрока — но строка остаётся в базе со статусом `void`, и
  откат возвращает её целиком. Фильтр по статусу сидит в трёх читателях (`catalog_from_db`,
  `cup_rows_from_db`, `docs_from_db`), поэтому правка проходит по всей связке строк игры и
  предпросмотр честно показывает `matches 2 414 → 2 413`, а не ноль изменений.

### Редактирование прямо на странице: `editor.js` + `db/serve.py`
Карандаши живут в самом интерфейсе, отдельной админки нет. Локально это два процесса:

```bash
set NST_EDITOR_TOKEN=… && set NST_EDITOR_NAME=aeros && python db/serve.py --port 8090
python -m http.server 8000
# затем открыть http://127.0.0.1:8000/soccer.html?edit=1
```

Без `?edit=1` страница остаётся ровно той, что публикуется: `editor.js` не рисует ни панели, ни
запроса (проверено в браузере — сети к `:8090` с обычной страницы нет). С `?edit=1` появляется
нижняя панель: ревизия базы, счётчик живых правок и очереди, поле токена и кнопки «очередь»,
«найти», «новая игра», «новый турнир», «игроки», «журнал», «опубликовать», «обновить», «скрыть».
Путь лороведа начинается с
«очереди»: `/api/queue` отдаёт неразобранные
задачи редактуры (что не так, ссылки источника, тур и стороны) и карточку строки, к которой задача
относится, — кнопка «к строке» открывает её без поиска по таблице турнира. Второй вход — клик по
строке матча: списки сезонов, спец- и командных турниров, «личные встречи» **и история игрока в его
карточке** (именно там видно, что разбор подставил не того человека; в режиме правки клик по строке
истории открывает карточку, а не профиль соперника). Третий вход — «найти»:
`/api/search?season=&tournament=&tour=&player=` ищет по разрядникам архива, а не по описанию
картинки («все игры Сезона 7 в 1/2 финала», «где вообще играл Bubnov»), сезоны и турниры для
подсказок приезжают вместе с ответом, а связка показывается одной карточкой. Победителем связки
всегда считается тот показ, который видит витрина: иначе поиск со скрытыми дублями подсовывал бы
человеку карточку второго показа. Скрытые дубли по умолчанию вне выдачи, для них стоит отдельный
флажок. Карточка правки: счёт, «снять с зачёта»,
«вернуть на зачёт», «вернуть строку на витрину», состав сторон, источники игры, «детали строки»
(место, дата, фаза, происхождение), «удалить игру» и предпросмотр дельты перед записью.
Предпросмотр показывает и то, что изменится в базе (поля с текущим и новым значением), и то, что
сдвинется на витрине (числа, затронутые игроки) — до записи.

На телефоне (≤720 px) панель живёт в одну колонку: планка кнопок становится строкой с горизонтальной
прокруткой — её высота предсказуема, и карточка правки ложится ровно над ней, а не под ней, —
кнопки не меньше 40 px, поля 16 px. Последние два числа не косметика: до 16 px мобильный браузер
самовольно приближает экран при фокусе, и человек перестаёт видеть, что правит.

**Кто играл в матче правится отдельно от того, как его показало табло** — `set-players`
(`python db/edit.py set-players 86062 "E_not & Bubnov" "Daria_P & Memori"`, в карточке — поля
«кто играл»). Человек пишет одну подпись стороны, а база делает из неё два хода, потому что
читатели берут имя из разных мест: таблица турнира и кубковый справочник печатают
`match_sides.label` (его правка сохраняет написание ровно как вписал человек), каталог сезона и
рейтинговый пул — `players.nick` через `side_players` (его пересобирает `sync_side_players` по
каноническим никам). Список карточек хранится и как текст — в `match_sides.roster`: журнал умеет
менять только колонки, так что откат восстанавливает игроков по этому тексту.

Порядок игроков внутри стороны задаёт `side_players.seat_index`, и собирает список Python, а не
`group_concat(...) order by ...`: вторая форма требует SQLite не старше 3.44, а версию движка в
рантайме публикации никто не обещал, и на 264 сторонах из 498 двухигроковых панель показывала
состав в порядке вставки — то есть перевёрнутым относительно подписи источника (из этих 264 в
227 первый игрок по местам совпадал с тем, что написал источник, и ни в одной — с порядком
вставки). Сохранение после такой предзаполненной карточки переписало бы пару в обратную сторону.
менять только колонки, поэтому откат восстанавливает состав по этой колонке, а не оставляет
сторону пустой. Новый ник заводит карточку через тот же `ensure_player`, что и импортёр, и
отказывается это делать, если slug уже занят другим игроком, — правка не плодит двойников.
Состав сверяется по **составу карточек**, а не строкой: `locate` приводит сторону к множеству
каноников, поэтому клик с «Bubnov & E_not» находит строку, которую источник записал как
«E_not & Tymoschuk». Неизвестный ник заводит карточку — и предпросмотр об этом предупреждает
(`created` в ответе: «заведутся новые карточки игроков: …»), потому что опечатка в нике родит
двойника, а не переименование; откат оставляет карточку в базе, но игрока без матчей страница не
показывает. И наоборот, правка по несуществующему id отказывает явно: строки пересоздаются
сборкой, и молчаливое «уже так» обмануло бы редактора.

**Источники, новые игры и новые турниры — тоже руки редактора.** `set-source` правит то, что
страница показывает в колонке счёта (`matches.note`), и список ссылок-доказательств
(`match_links`): подпись идёт по всей связке строк, а ссылки остаются у той строки, на которую
смотрел человек — доказательство рейтинговой копии придумывать нечем, и молча оно бы
умножилось. `add-match` заводит игру там, где источник её описал словами, а таблица потеряла:
`source = 'manual'`, `manual = 1`, стороны и игроки строятся тем же кодом, что у импортёра, а
дубль отсекается до вставки (`twin_match` отказывает и говорит, какую строку править вместо
этого). `add-tournament` заводит рамку-документ со **списком игр, оставленным пустым** — игры
навешивает читатель, иначе порядок ключей страницы поедет; `set-doc` правит саму рамку и ставит
документу `manual = 1`, чтобы носитель его больше не перезаписывал. Пустая подпись новой игры
берётся из счёта: для строки турнира счёт показывает именно `note`, и без этого игра вышла бы из
таблицы с пустой ячейкой, а история игроков её вообще не заметила бы.

**Где игра лежала, когда играли и чем закончилось — правится в блоке «детали строки».**
`set-place` (тур, дивизион, этап) идёт по всей связке: страница группирует строки по туру и
дивизиону, и ошибка разбора живёт именно там. Перенос молча сломал бы идемпотентность импорта —
носитель опознаёт строку по «документ + тур + стороны + счёт», поэтому правка оставляет импортёру
память о прежнем месте (`matches.source_place`), и `_load_existing_keys` регистрирует **оба**
ключа: без этого следующий импорт принёс бы ту же игру вторым рядом (проверено на копии: с
`source_place` дубль прячется за ручную строку, без него — выезжает на витрину). `set-date`
(played_on + дословная дата источника) — не косметика: рейтинг проигрывает матчами по времени, и
партии без года `unrateable_reason` не даст встать в Elo; точность (`exact`/`month`/`season`)
база выводит из формы сама. `set-phase` (овертайм, буллиты, цена плей-офф) сверяется с исходами
до записи, повторяя два инварианта `db/validate.py`, — иначе правка прошла бы в базу и уронила бы
сборку, а человек узнал бы о проблеме только там. Победа в овертайме или по буллитам стоит 0.75
вместо 1, плей-офф играет при K=32, поэтому предпросмотр фазы показывает сдвинувшийся Elo.
`set-provenance` (носитель, ключ, где искать, страница, дословный текст) правит **одну строку, а не
связку**: `(source, source_ref)` в базе уникален, и общий ключ на две строки одной игры — это
конфликт, а не порядок.

**Удаление — единственная правка с двумя кликами.** Кнопка «удалить игру из базы» сначала вооружается
(«нажми ещё раз»), потом пишет; предпросмотр у неё не нужен, потому что предпросмотр = отмена.
`drop_match` уносит строку вместе со сторонами, составом и ссылками (каскад по FK) и записывает всё
это снимками `exists`, поэтому откат возвращает связку байт-в-байт (проверено на копии: −2 матча,
−4 стороны, −4 состава → откат → счёт и содержимое строк совпали). Указатели внутри связки
(`duplicate_of`, `hidden_by`) гасятся **до** удаления и по всей связке сразу: каталожная строка
ссылается на пуловую, и удаление их вперемешку ловит FOREIGN KEY на середине обхода. Ссылка извне —
отказ («на строку #180 ссылается 1 других — сначала разбери дубли»), задача редактуры на удалённую
игру остаётся в очереди без строки. `drop_tournament` берёт только пустой документ: пока в нём есть
игры, база называет их число.

**Карточки игроков: «игроки» в панели — поиск по нику, переименование и слияние.**
`GET /api/players?q=` ищет подстрокой (`%` и `_` внутри ника — обычные символы, запрос экранируется),
`rename-player` меняет `nick` и `slug` вместе, иначе адрес карточки начал бы вести в чужой профиль, и
отказывает, если slug уже занят. `merge-player` идёт по направлению, которое выбрал человек: сначала
«оставить эту», потом «слить эту в #N» на той, что уходит, — ушедшее написание становится алиасом со
`source = 'editor'`, партии переезжают на оставленную карточку, а если эти двое когда-нибудь играли
друг против друга, слияние отказывает до записи (иначе игрок оказался бы в обеих сторонах матча).
Откат такой операции — два прохода: сначала возвращаются удалённые строки (по `RESTORE_ORDER`,
родитель раньше ребёнка), потом применяются правки колонок; одним проходом перестановка `player_id`
падала на FOREIGN KEY.

**Откат работает по метке операции, а не по секунде.** Журнал умеет обновлять колонки, поэтому
создание и удаление строки записано псевдо-полем `exists` со снимком строки (`corrections.op` —
метка операции): `undo last` откатывает ровно одну операцию, а не всё, что успели записать в ту же
секунду. Проверено сквозняком: новая игра → сборка → «Финал Kunio 5:2 mafuta» на странице и
+1 матч, +7 голов, +1 видео в шапке → откат в интерфейсе → сборка → 22/22 байт-в-байт.

**Откатить можно любую операцию, а не только последнюю.** Пока человек разбирался с одной правкой,
база могла принять другую, и снимать надо ту, которую он назвал: `undo op:<метка>` берёт все
действующие записи метки и идёт по тому же двухпроходному порядку, что и `last` (сначала возврат
удалённых строк по `RESTORE_ORDER`, потом правки колонок). Метку печатает `log` (`[op:…]`) и ответ
любой операции (`"op"` в JSON), `/api/log` несёт `op` и `op_live`, и панель журнала рисует на каждую
группу кнопку «откатить операцию целиком (N полей)». Проверено в браузере на двух живых правках
поверх друг друга: откат по метке более старой вернул `played_on` и `date_precision` обеих строк
связки, оставив `tour` и `source_place` последней операции нетронутыми. Откат по id записи
возвращает **одно** поле — это ловушка, а не фича: ник вернётся, а его `slug` нет; зафиксирована
тестом. Пока правка в пути (предпросмотр или запись — секунды, а на больших разделах больше десяти),
панель занята: все кнопки неактивны, повторный клик не порождает второго запроса, вооружённая кнопка
удаления разоружается, а в статусе читается «выполняется: запись места строки · 4 с».

Игры Кубка лиг считаются матчами везде, где считается остальное архива: с 2026-11-03 они
попадают и в историю игрока (отдельной категорией `cup`, как спецтурниры — поэтому сезонные
лидеры бомбардиров и «на ноль» от них не двигаются), и в таблицы сезона, и в личные встречи.
Раньше они входили в числа витрины, но не в карточку игрока — один и тот же матч считался и не
считался. Написание кубкового справочника («LiptOn», «Tymoschuk») в историю не попадает: там
каноник из `portal/name_tables.py`, иначе игрок заводился бы двумя строками (92 → 98 профиля).

Молодёжный чемпионат играется парами, и «lenin1st & ectoPower» — не игрок: `add_special_records`
разбивает сторону на двух, записывает каждому партнёра и соперника целиком. До этого восемь игр
молодёжки числились в таблицах и в общих числах, но не попадали ни в одну карточку (профилей было
92, стало 96). Написание «sokol» из того же турнира живёт в `ALIAS_MAP`, а не в
`PLAYER_CLEAN_MAP`: второй словарь опечатывается строчными, на них держатся ключи
`vk_match_sources_lookup.json`, и правка там тихо оторвала бы игроку ссылки на посты и видео.
По написанию шапки темы это два разных VK-аккаунта (лиговый «Sokol» — 753577095, молодёжный
«sokol» — 505081745, он же «ZaSashku» 2019 года), но решать, кто один человек, не машине:
владелец сказал объединить, и алиас ведёт обе формы в «Sokol».

Обратный случай, где слияние ломало данные: «Palka Palych» и «PacnyTHuK» справочник считал
одним игроком, но в 2-м Молодёжном они сошлись друг против друга в одной встрече (комментарий
22578 темы 41270759), а в списке участников у них разные id — 9313314 и 112974978. Один игрок
оказывался в обеих сторонах матча, и это ловил `db/validate.py`; алиас разделён. Следствие
видимое: восемь строк плей-офф Сезона 6, где источник пишет «Palka Palych», ушли с карточки
PacnyTHuK на отдельную; Elo и мастер-таблица не шевельнулись — это строки каталога, не пула.
Градус внимательности тут вот какой: `ALIAS_MAP_LOWER` строится из `ALIAS_MAP` строчными
ключами, поэтому написания, которые должны развестись, обязаны быть прописаны **оба** — иначе
заглавный вариант молча провалится в чужой строчный алиас.

Строка на странице не имеет идентификатора, поэтому карточка ищет игру в базе по описанию
(пара, счёт, тур) и показывает **все** подходящие строки; связку «строка страницы + матч
рейтингового пула» (Сезоны 8–9 лежат в базе так и есть) она сворачивает в один кандидат и правит
сразу обе — иначе таблица обновилась бы, а Elo продолжал бы считать старое. Строка без счёта
(суперфинал Сольного по пенальти, выводные встречи молодёжки) показывает в колонке счёта не «N:N»,
а подпись источника, поэтому клик по такой строке сверяется по подписи: иначе редактор не смог бы
открыть ровно те строки, ради которых его и зовут. И наоборот: как только человек вписал в такую
строку счёт, `set_score` уводит подпись за числами (`matches.note` → «7:4»), иначе правка осталась
бы в базе, а таблица турнира продолжала бы рассказывать, что счёта нет. Откат возвращает и числа,
и подпись — обе лежат в журнале.

Права: сервер не поднимается без `NST_EDITOR_TOKEN`, чужой `Origin` отбивается 403-м, подпись в
журнале берётся из `NST_EDITOR_NAME`, а не из запроса. Для публичного сайта тот же `db/api.py`
обслужит Vercel-функция поверх Neon — адрес она подставит в `<meta name="nst-editor-api">`, и
интерфейс не изменится.

### Публичный транспорт правки: `api/handler.py`
`db/serve.py` был локальным: панель на опубликованном сайте стучалась в `http://127.0.0.1:8090`,
которого у читателя нет. Теперь те же восемь ручек отдаёт Vercel-функция — `api/handler.py`
определяет `handler` как **подкласс `serve.Handler`** (Vercel умеет загружать из файла в `api/`
класс, наследующий `BaseHTTPRequestHandler`), поэтому список операций, обязательные аргументы,
проверка токена, allowlist `Origin`, лимит тела, коды и русские тексты отказов задаёт
`db/serve.py`, а не вторая копия где-то рядом.

Своё у функции три страховки: маршрут (Vercel может подменить исходную ручку именем функции —
восстановление через `nst_handle`/`x-now-route-matches`), адрес базы (`NST_DB_PATH`, по умолчанию
та же `data/nst.db`) и JSON на аварию внутри GET, которую `db/serve.py` перехватывает только на
записи. `vercel.json` добавляет `functions` (лимит 60 с, `excludeFiles` для `tests/`, `archive/`,
`scratch/`) и `routes`: `/api/*` → функция, дальше `handle: filesystem` — статика отдаётся ровно
как раньше (ссылки в портале все с расширением, поэтому `cleanUrls` ничего не держит).

- Переменные: `NST_EDITOR_TOKEN` (без него функция не отвечает), `NST_EDITOR_NAME` (подпись в
  журнале), `NST_EDITOR_ORIGINS` (список источников), `NST_DB_PATH`, и `NST_EDITOR_API` — адрес
  сервера правки, который сборка подставляет в `<meta name="nst-editor-api">` вместо
  `http://127.0.0.1:8090`; на Vercel это `.`, чтобы панель ходила в тот же источник.
- **Записи в проде пока нет:** файловая система функции доступна только на чтение, поэтому
  `persist: true` вернёт 500 с текстом отказа, а предпросмотр работает (он и так считается на
  копии). Постоянной базой правок должен стать серверный Postgres (Neon) — под него оставлено
  ровно одно место: `api/handler.py::bind_database`. Драйвера нет сознательно: боевой базы там
  ещё нет, а непроверенное соединение в путь записи архива вставлять нельзя.
- Проверка без портов и без живого Vercel — `tests/test_transport.py`: одна и та же сборка запроса
  прогоняется через `serve.Handler` (эталон) и через функцию, и ответы сравниваются целиком,
  кроме волатильного (`op`, `recomputed_in_ms`, `Date`); отдельным тестом — что в `api/` нет
  копий `OPERATIONS`/`REQUIRED_ARGS`/`MAX_BODY`.

### Очередь публикаций: `db/publish.py`
Выкат по-прежнему делает сборка — перерисовывать прод-сайт по клику никто не просил. Нужное
другое: лоровед без терминала должен видеть, что его правки **ждут выката**, а не растворились.
Поэтому запрос публикации — это запись в очередь, а не действие: таблица `publish_requests`
(шаг в `db/schema.sql`, в журнал правок она НЕ пишется и `undo` её не откатывает) помнит отпечаток
базы, число действующих правок на момент постановки, автора и одной строкой — что публикуем.

```bash
python db/publish.py request --note "сезон 9 разобран до последней строки"
python db/publish.py list
python db/publish.py apply          # взять самый старый запрос и запустить python build_all.py
python db/publish.py close          # закрыть очередь после ручного build_all.py
```

- В панели — кнопка «опубликовать» рядом с «журналом»: поле «что публикуем», двухшаговое
  подтверждение (выкат ничего не разрушает, но это тоже dangerous action), список очереди и
  счётчик «на выкат поставлено: N» в статус-строке. Данные приходят из `GET /api/publish`,
  который отдаёт ровно `pending()` и число живых правок — ту же цифру, что показывает состояние
  базы, а не вторую, посчитанную по-своему.
- Отказы: «публиковать нечего: в базе нет ни одной действующей правки»; «запрос #N на ревизию …
  ещё не закрыт — второй на тот же срез ставить смысла нет»; «запрос публикации без подписи
  редактора не ставится»; если шага схемы ещё нет — модуль говорит это прямо, а не делает вид,
  что очередь пуста.
- **Почему очередь закрывается по факту сборки, а не по совпадению отпечатка.** Живые правки после
  выката никуда не деваются — они защищают строку от импортёра, — а `revision` считается по id
  строк, которые пересборка меняет (одна и та же игра за день была 198565 → 210449 → 216391).
  Закрытие «по совпавшему отпечатку и нулю живых правок» не сработало бы никогда. Сборка же
  публикует базу целиком, поэтому `apply` после успешного `build_all.py` закрывает и те запросы,
  что поставили, пока сборка шла.
- `apply` запускает сборку тем же интерпретатором (`sys.executable`, рабочий каталог — корень);
  при провале запрос помечается `failed`, а в `detail` ложится хвост вывода сборки (25 строк) —
  человек видит причину, а не «что-то упало».
- Тесты (`tests/test_publish.py`, 22 проверки) покрывают отпечаток запроса, оба отказа, порядок
  очереди, `claim`/`close`/`fail`, идемпотентность шага схемы (два настоящих прогона
  `db/build_db.py` на копии) и равенство ручки `pending()`.

### Тесты правки: `tests/`
```bash
python -m pytest              # 161 тестов, ~27 секунд
python -m pytest tests/test_refusals.py -k provenance
```

Живую базу тесты не трогают: на каждый тест берётся копия `data/nst.db` (1,9 МБ) во временный
каталог, и операция, которая что-то сломает, остаётся внутри одного теста. Строки ищутся
**свойством** («матч 1×1, где первая сторона выиграла», «строка турнира без счёта», «строка
страницы со своей копией в пуле»), а не фиксированным id: id меняет каждая пересборка базы, и тест
с номером строки протухал бы ровно тогда, когда он нужнее всего.

Девять файлов проверок:

- `tests/test_operations.py` — каждая операция применяется и откатывается, а база обязана
  вернуться к исходному срезу. Сверяется не «поле поменялось», а девять таблиц целиком
  (`matches`, `match_sides`, `side_players`, `match_links`, `players`, `player_aliases`,
  `tournament_docs`, `stages`, `tournaments`), кроме `updated_at` — его правка пишет всегда.
  Где полный возврат принципиально невозможен, это написано в тесте открыто: пересборка состава
  после отката вставляет `side_players` заново (номера `id` новые), а карточка игрока, заведённая
  правкой, после отката остаётся.
- `tests/test_refusals.py` — отказы. Текст отказа проверяется намеренно: лоровед читает именно
  его, и «IntegrityError: constraint failed» ему не скажет ни о чём. Здесь же таблица
  `phase_problem` (повтор двух инвариантов валидатора) и семантика журнала: `undo last` откатывает
  операцию целиком, а `undo <id>` — ровно одно поле (ловушка: `nick` вернётся, `slug` нет).
- `tests/test_edit_api.py` — слой над ядром: предпросмотр не сдвигает ревизию и не оставляет
  записей журнала, `expect` отклоняет запись поверх чужой правки, `locate` сворачивает связку в
  один кандидат и не делает из скрытого дубля самостоятельную строку, `serve._edit` отсекает
  запросы без обязательных полей. Здесь же поиск по разрядникам (`api.search`): сезон и турнир
  сужают выдачу и подсказки, скрытые дубли приходят только по явному флагу, победителем связки
  остаётся видимый показ, а `%` и `_` в написании не становятся маской.
- `tests/test_transport.py` — дифференциальная сверка: один и тот же запрос проходит через
  `serve.Handler` и через `api/handler.py` без портов, ответы сравниваются целиком, а отдельным
  тестом проверяется, что в функции нет второй копии списка операций.
- `tests/test_publish.py` — очередь публикаций: отпечаток запроса, оба отказа, старшинство очереди,
  `claim`/`close`/`fail`, идемпотентность шага схемы и равенство `GET /api/publish` функции
  `pending()`.
- `tests/test_store.py` (11) — точка подключения и схема: ни один модуль не зовёт драйвер мимо
  `db/store.py`, путь по умолчанию один, миграция `side_players`/`player_aliases` к собственному
  `id` сохраняет номера строк вместе с разрывами в них (иначе старые записи журнала указывали бы
  на чужие строки), второй прогон схемы ничего не двигает, а `--from-store` не зовёт шаги,
  которые пересобирают срез.
- `tests/test_pg.py` (14) — генератор Postgres: переводятся все таблицы, колонки стоят в том же
  порядке (по ним сверяются снимки журнала), идентичность `GENERATED BY DEFAULT`, а не `ALWAYS`
  (откат вставляет id явно), часы остаются текстом в формате UTC, `PRAGMA` и JSON-функции SQLite
  не переживают перевод, `?8` превращается в `%(p8)s` и может встречаться дважды. Главный тест
  — охрана: константы пути правки собираются из модулей, и любой новый SQLite-изм упрётся именно
  сюда, а не в боевую базу. Живого Postgres в окружении нет, поэтому проверяется текст.
- `tests/test_importers.py` (3) — контейнеры собранной базы: у документа один турнир-рамка, а
  строка живого календаря стоит в сезоне своего документа. Без этого импортёр календарей заводил
  второй «VI Командный Чемпионат по Goal 3» с сезоном «—», и половина чемпионата жила отдельно.
- `tests/test_names.py` (3) — канонизация написаний: `clean_alias` обязана вернуться, а не уйти в
  рекурсию на незакрытой скобке (ник, обрезанный на середине строки комментария), и обязана
  держать врозь тех, кого путают гомоглифы («Palka Palych» и «PacnyTHuK» играли друг против друга).

`pytest` — dev-инструмент, как `ruff`: в `requirements.txt` его нет. `pytest.ini` нужен затем,
чтобы голый `python -m pytest` не собирал исследовательские скрипты `scratch/test_*.py` — они не
тесты, а одноразовые замеры.

Что нашёл этот прогон (все три — настоящие ошибки, а не хрупкие тесты): после отката правки
происхождения `manual` оставался на парной копии строки и вырывал её из пересборки базы; при
последнем откате флаг не снимался со всей связки; и `_date_shape` пропускал несуществующее
45 июня, потому что регулярка проверяет форму, а не календарь.

### Контроль целостности: `db/validate.py`
23 инварианта базы, которые `build_all.py` проверяет перед генерацией страниц: у матча есть
стороны и они пронумерованы подряд, исход согласован со счётом (равный счёт прощается только
ноге не `regular`-этапа — её решает серия, и для неё проверяется, что исход либо честная
ничья, либо пара победа/поражение), технический матч имеет ровно
одну сторону `none`, `hidden_by` не цепочится и не пересекает срезы, `source_ref` не
повторяется, дата не в будущем и не «1970 год вместо года», точность даты согласована с самой
датой, стадия принадлежит своему турниру, в сторонах нет одного игрока с двух сторон, ник и
slug игрока уникальны, игра турнира привязана к своему документу (и не приписана чужому), у
строки документа есть обе стороны — иначе читатель её потеряет, и игры одного документа лежат
в одном турнире-контейнере (у рамки сезон один, и разъезд превращает чемпионат в два). Отдельно
сверяется справочник
написаний: каноник не должен переименовывать уже заведённого игрока (так лиговый «Sokol» не
уехал в «ZaSashku»). Ненулевой код остановки — сборка
падает, а не печатает цифры с дефектом.

### Дашборд и мастер-таблица — не одно и то же
`python build_final_analytics.py` перегенерирует **из данных** витрину `nekketsu_dashboard.md`
и кладёт аналитический срез в `data/analytics_master_table.json`.

`nekketsu_master_table.json` — тоже производный файл, не замороженные данные. Его пишет
`python build_master_table.py` из того же пула матчей: модель рейтинга в `portal/elo.py`
(формула, порядок партий, штраф за простой), справочники,
которые ведёт человек, — в `portal/master_tables.py` (тиры, титулы, архетипы, «кумиры»).
`build_all.py` перегоняет его перед сборкой страницы, поэтому править цифры в самой
мастер-таблице бессмысленно: их перезапишет сборка. Менять надо пул матчей и справочники.

Метки времени в файле нет — вместо неё `source_fingerprint`: отпечаток пула матчей. Он
сдвигается, если изменился хотя бы один матч, и не меняется при повторной сборке одного и
того же пула, так что сборка остаётся детерминированной и по-прежнему сверяется по хешам.

### Единая база матчей (`data/nst.db`)
Все матчи сводятся в одну SQLite-базу: схема — `db/schema.sql`, наполнение —
`python db/build_db.py` (рейтинговый пул: снапшот Sportcup + рукописные блоки) и
`python db/import_stores.py` (каталог матчей сезонов, игры Кубка лиг Сезонов 2–7, спецтурниры,
командные 2×2 — из носителей и справочника, до фильтрации витрины: база хранит и те строки,
которые страница сейчас отсеивает). 3 024 строки: 402 пула + 2 377 каталога + 81 кубок + 148
спецтурниров + 16 командных. `python db/verify_db.py` проверяет, что база отдаёт ровно тот пул,
из которого собран сайт, что мастер-таблица, посчитанная из базы, совпадает с посчитанной из
Python-списка, и что документы и кубковые строки собраны так же, как их дал носитель.
`python db/flag_twins_for_review.py` складывает в `incoming` пары «страница ↔ пул», которые
похожи, но механически не доказаны (разные подписки раунда), — это очередь на решение
редактору, а не основание для автоматической склейки.
`python scratch/audit_final.py` прогоняет сверку целиком: носители против базы, база против
того, что реально показывает страница, числа заголовка, пересчитанные из payload, профили
против имён в таблицах, даты и очередь на решение. Он и нашёл восемь потерянных игр молодёжки.

Строка пула вставляется один раз и больше не перезаписывается — иначе правка человека из
редактора пропала бы при каждой сборке. Из-за этого изменение в `data/sportcup_decisions.json`
до уже занесённой игры само не доходит, поэтому `db/build_db.py` обновляет у существующих
пуловых строк одно поле — `note` (и только там, где `manual = 0`) и печатает «пометку счёта
обновлено N». Так работают пометки из ключа `score_note`: Sportcup пишет игру, решённую серией,
её счётом буллитов (67 строк Сезонов 8–9 помечены `overtimeWin`, и ни одна не равным счётом —
флаг значит «была доигровка», а не овертайм), а тема говорит основное время: «1:1 (ПК 5:3)» для
239 и «1:1, 3:6 пен.» для 270. Счёт остаётся как у источника — он и в Elo даёт 0.75/0.25, — а
правда о нём ложится в `note`, которое панель правки показывает строкой «счёт источника» и
умеет переписать. Флаг `ot` у таких строк пока врёт: поднять его до `pk` — отдельный шаг (#75,
вариант C), потому что это меняет и витринные индексы овертаймов.

Открытый вопрос ровно там же закрыт решением по архиву (2026-11-03): одну и ту же кубковую ногу
Сезонов 4–6 источники описывают **три раза** — строка вики-таблицы сезона (помечена как
псевдо-кубковая и со страницы снята), строка справочника «Кубок лиг» (показывается на странице) и
матч рейтингового пула (Elo её считает). Разбор такой:

- **Там, где identity доказана, она записана.** `db/close_cup_pairs.py` склеивает строку кубка с
  пуловой ногой по «сезон + пара + счёт + тот же раунд» (нормализованно: «Финал» = «Финал
  Кубка») — это `duplicate_of` на строке страницы, 10 пар. Числа не двигаются: `duplicate_of`
  ничего не прячет (для этого есть `hidden_by`), а в Elo остаётся пуловая строка.
- **Остальное — не копии, а разная granularity.** 22 пуловые «невидимые» ноги — это legs серий
  (в одном 1/2 финала mafuta ↔ RVD шесть игр с разными счётами), а справочник кубка записывает на
  раунд **одну** строку. То есть таблица кубка — сводка, а пул — протокол. Ни то ни другое нельзя
  вывести из другого, поэтому ничего не переписывается: справочник остаётся показанным видом
  кубка, пул — рейтинг-протоколом.
- **Спорное не склеивается.** 10 пар остались в `incoming` batch `twins_2026-11-03` (например,
  ectoPower 4:0 Rock в 1/4 финала против того же счёта в 1/2 — в серии такое бывает); автоматом
  они не склеиваются, потому что `duplicate_of` на строке пула убрал бы игру из рейтинга.

Что читается из базы — уже всё, что страница показывает как матч: `build_all.py` синхронизирует
её перед сборкой; мастер-таблица считается из `v_rating_pool`; `portal/build_soccer.py` берёт
каталог матчей из `db/catalog.py: catalog_from_db()`, игры Кубка лиг Сезонов 2–7 — из
`db/catalog.py: cup_rows_from_db()`, профили и истории игроков — из `db/pool.py`, спец- и командные
турниры — из `db/docs.py: special_from_db()` и `team_from_db()`. В пути сборки страницы
`build_final_analytics` больше нет: он остался на стороне сборки данных (`db/build_db.py`).
Файлы-носители (`early_seasons_matches.json`, `all_vk_seasons_matches.json`,
`wiki_seasons_matches.json`, `special_tournaments_data.json`, `team_tournaments_data.json`) и
справочник `portal/cup_tables.py` теперь питают только импортёр: правка в базе больше не
«перетирается» выгрузкой. В `cup_tables.py` от справочника остались подписи «чемпион» и
«финалист» — это метки, а не матчи.

У кубковой строки своя форма: без `stage`, `ot`, `pk` и `source`, с пустыми `vk_url`/`vk_page` и
`vk_date` = год сезона строкой. Читатель возвращает её именно так, иначе payload страницы
разъедется по байтам. Ники сторон берутся из подписей (`match_sides.label`), а не из
`players.nick`: справочник помнит игроков так, как их записал кубок («Tymoschuk» рядом с
«Bubnov», «LiptOn» рядом с «Буц»), и сводить эти написания молча читатель не имеет права — это
решение человека, а не нормализации. `source_ref` у строки позиционный (`CUP:Season 4#14`).

Турнирный документ — это рамка (заголовок, категория, описание, хроника, призовой фонд, итоговые
таблицы `groups` / `divisions` / `playoff` / `ladder`) и список игр. Рамка лежит в
`tournament_docs.payload` как JSON, а игры — в `matches` с `doc_id`: одна и та же игра не может
жить в базе дважды. При чтении список игр возвращается на то же место в документе (он хранится
пустым), поэтому страница получает ровно те же словари с ровно тем же порядком ключей. Счёт
«2:0» в таблице турнира читатель берёт со сторон матча, а не из рамки: правка в базе доходит до
таблицы, и статистика игроков за ней тоже. Надпись словами («Победа Kunio/Memori», «🥇»)
остаётся как её записал источник — числам там делать нечего. Пока рамку правят в файле,
`python db/verify_db.py` сверяет документы с носителем байт-в-байт.

Зачем у каталога такой придирчивый обратный формат: база обязана отдавать строки со теми же
ключами и в том же порядке, что их строит `portal.match_catalog`, иначе страница перестанет
сверяться байт-в-байт. Отдельные грабли, которые это держит: `ot` и `pk` — независимые флаги
(230 строк подняты обоими, поэтому в базе есть значение `overtime_penalties`), а `vk_page` и
`vk_date` — числа, хотя столбцы текстовые.

Матч хранится как **стороны и их участники** (`match_sides` + `side_players`), а не как пара
`p1`/`p2`: 1×1 — две стороны по одному игроку, клубный 2×2 и мол. чемпионат — по двое,
мини-баттлы — стороны с произвольным числом участников плюс `series`.

Дублем считается только та же игра из того же места: совпавший `source_ref`, либо один и тот же
документ источника (страница вики, пост VK или таблица турнира в `tournament_docs`) **в том же
туре** при той же паре и счёте. Оба
условия нужны: пост покрывает тур целиком, и шесть разных матчей давали ту же пару и тот же счёт
в другом туре. И наоборот — два одинаковых счёта одной пары в одном туре могут быть настоящими
двумя играми («daz vs yoxter 0:1, 0:1» в 8 туре, награждённые 3:0 в двухкруговике Сезона 8),
поэтому совпадение счёта само по себе доказательством не считается и такие пары не склеиваются.
Кроме того, `db/close_early_mirrors.py` прячет **зеркальные** строки раннего архива: Сезон 1
был перенесён из Google-таблицы матрицей «строка × столбец», и каждая встреча легла дважды —
`Memori 4:0 Ric25` и `Ric25 0:4 Memori`. Правило ограничено `source = 'early_archive'` ровно
потому, что в остальных сезонах зеркальный счёт в одном туре значит «ноги кончились одинаково»,
а не «строка продублирована»; дублем оно считает только строку, у которой стороны стоят наоборот
и счёт перевёрнут — одной перестановки чисел мало, потому что две настоящие игры пары на одной площадке
легко дают «2:1» и «1:2». С тех пор регулярный чемпионат Сезона 1 пересобирается из снимков
таблиц (`collectors/build_season1_archive.py`) по одной строке на игру, и прятать в нём стало
нечего: от витрины скрыто 45 строк, все — из других сезонов. Живой импорт (`db/import_live.py`)
добавляет 343 строки: 91 встречу регулярки IV и VI Командных, 134 строки группового тура
2-го Молодёжного (из них две — «ТП обоим») и 118 строк турниров по пенальти. Витрина показывает
**2 574 матча**, в шапке сайта — **3 043 матча, 19 372 гола, 1 678 видео, 102 игрока**
(командных 107 вместо 16).
`python db/import_stores.py` в конце вызывает `db/close_sportcup_pairs.py`: игры Сезонов 8–9,
которые страница показывает повторно, склеиваются с матчам рейтингового пула по uuid из
снапшота Sportcup (порядок проекции `from_sportcup_api` совпадает с порядком пула, поэтому
склейка идёт по построению, а не по «похожести»). Поле `in_rating_pool` решает, что считается в
Elo: импорт страницы в рейтинг сам не попадает, но партию в него берёт редактор — `set-rating` и
`rate-scope` (см. «Математика рейтингов»).

### Матчи Сезонов 8–9 и работа без сети
Эти сезоны существуют только в Sportcup API, поэтому их ответы заморожены в
`data/sportcup_games.json` (коммитится в репозитории). Сборка читает именно файл:
**она полностью работает без сети** и не зависит от того, жив ли sportcup.org.

Обновить заморозку — после новых туров или чтобы проверить, не изменился ли ответ API:

```bash
python collectors/sync_sportcup.py            # перезаписать снапшот с живого API
python collectors/sync_sportcup.py --check    # только сравнить снапшот с API, ничего не писать
```

Если у одного из шести стейджей нет данных ни в снапшоте, ни в сети, сборка
остановится с явной ошибкой — молча потерять половину лиги она больше не может.

### Живая сверка с сообществом (`collectors/vk_recheck.py`)

Выгрузить актуальное состояние группы и сравнить его с базой:

```bash
python collectors/vk_recheck.py topics                # список обсуждений (375)
python collectors/vk_recheck.py comments --scope soccer  # комментарии футбольных топиков

python collectors/vk_recheck.py docs                  # документы сообщества
python collectors/vk_recheck.py wiki                  # тексты вики-страниц
python collectors/vk_reconcile.py                     # → data/vk_recheck_<дата>.md + .json
```

Что в комментарии нога, а что нет, решает `collectors/vk_reconcile.py: legs_of` — и правила эти
взяты из текстов самих тем, а не придуманы: блок «ПРИМЕР ВЫКЛАДЫВАНИЯ РЕЗУЛЬТАТОВ» в шапке каждой
темы — образец оформления, а не протокол (из него однажды выросла выдуманная игра
«Memori 3:0 Centurion» в каждом сезоне 2–7); одна счёт-пара в скобках доигрывает предыдущую ногу —
золотой гол по регламенту («5-5 (1-0)») или серия («1-1 (4-3 пен)»); несколько пар в скобках
перечисляют ноги, и счёт перед ними — итог встречи; слово серии без запятой («6-6 PK 5:4»)
относится к предыдущей ноге, а с запятой («3:0, 8:5пен.») — это вторая нога. Если в скобках стоят
и основной счёт, и доигровка («5:4 (3:3 - основное время, 2:1 - буллиты)»), ногой считается
основной, но итог снаружи тоже принимается: вики-календари Сезонов 2–7 записывают ту же встречу
итогом с пенальти, и на 284 строках это политика источника, а не ошибка. Сольные турниры по
пенальти хранят пару ног одной строкой-суммой: «Буц - Christian - 1:5» и «- 3:5» из комментария 9742
— это «4:10» в базе, и сверка принимает сумму ног той же пары внутри комментария. Нераспознанные
написания считаются по паре, а не по ноге, иначе строка из четырёх ног раздувает раздел. Правила
проверяет `tests/test_comment_parser.py`.

Ещё два правила снимают строку с расхождений, не трогая базу, и попадают в отчёте в раздел
«Снято с расхождений» (`items` остаётся машинным списком настоящих споров, `resolved` — справкой о
том, что сверка отменила сама):

* **переигровка отменяет раннюю запись** (`REPLAY_MARK`, окно `REPLAY_WINDOW` в 40 комментариев):
  те же стороны в том же порядке названы позже другим счётом, база согласна с поздним, а между
  строками есть слово переигровки или вопрос «в итоге?». Так тема 52002075 отменила запись 1:4
  (коммент 31240) переигровкой 0:2 (коммент 31249), а тема 54769667 — 3:1 (32957) ради 2:0 (32965).
  Окно и маркер нужны затем, чтобы правило не стерело настоящее расхождение: в круговом турнире
  та же пара встречается несколько раз, и без них поздняя игра другого тура заглушила бы ранний спор.
* **итог серии — не игра** (`series_total`): если сумма чисел равна числу ног пары в этом турнире,
  а победы по ним дают ровно эти числа, строка «Yuliy_Cezar vs Ryumaru 3 - 0» (коммент 32977)
  читается как счёт серии над уже занесёнными ногами 2:0, 5:2 и 2:1.

Четвёртое правило того же происхождения живёт в `legs_of`: «1:1, 3:6 пен.» — одна игра (ничья
основного времени и решающая серия), а не две ноги, потому что Sportcup записывает такую игру
счётом серии. До этого сверка требовала в базе несуществующую вторую ногу и рисовала расхождение.

Живые результаты, которых нет в шести носителях, заносятся отдельно: `python db/import_live.py
--extract` выделяет встречи из вики-календарей в **носитель** `data/vk_live_matches.json` (он
коммитится и читается глазами — тот же приём, что со снапшотом Sportcup), а шаг сборки
`db/import_live.py` грузит его в `matches` с `source = 'vk_live'`. Куда ложится строка, решает
`import_live.containers`: имя носителя сопоставляется с документом турнира (и сезон берётся из
его рамки), а если документа нет — с сезонной рамкой (`kind = 'league'`): так игры дивизионов
раннего чемпионата попадают в тот же турнир, что и строки Google-таблицы, а не заводят двойник.
Обычный импорт таких строк не касается (`reset_previous_imports` их исключает), `db/verify_db.py`
сверяет рамку документа с носителем тоже без живого среза и отдельно сообщает, сколько живых
встреч добавлено. Разбор
общего формата — `portal/live_sources.py` (его же читает `collectors/vk_reconcile.py`, чтобы
сверка и занесение понимали источник одинаково). В сверку берутся обсуждения чемпионатов лиги
(`SOCCER` без `FOREIGN` в `collectors/vk_recheck.py`): «Soccer Hen» оттуда убран — ром тот же,
но розыгрышей с таким названием в архиве нет, а заголовок «…Soccer Hen. Season I» давал подпись
«сезон №1» и превращал чужой турнир в потерянные игры раннего чемпионата.

Групповой тур 2-го Молодёжного разбирается из трёх кусков источника (`portal/youth_sources.py`):
гугл-таблица турнира даёт календарь (21 встреча на дивизион, каждый с каждым, по четыре ноги) и
сводку (встреч, ног, побед, побед и поражений по пенальти, очков), а тема 41270759 — счёта ног.
Если сводка даёт паре ноль встреч, а тема о её играх молчит, встреча всё равно ложится в базу
одной строкой «не сыграно» без голов и без победителя: календарь полон, и дыра в нём читалась бы
как потерянная игра, а не как несыгранная (проверка — `tests/test_youth_group.py`).
Листы таблицы выгружаются отдельным файлом в `data/gsheet_youth/<gid>.csv` — `--extract` сеть
не трогает и работает с тем, что лежит на диске (свежий лист: `…/export?format=csv&gid=<gid>`,
список `gid` отдаёт `htmlview` той же таблицы).
У Сезона 1 тот же приём: снимок трёх листов лежит в `data/gsheet_season1/`, а весь регулярный
чемпионат из них вытаскивает `python collectors/build_season1_archive.py` — по одной строке на
игру, `Тур 1…18` и дата приходят из календаря. Матрица даёт ноги (скобка в ячейке значит
«гостевая», а «13т» — что игра перенесена и её не было), календарь их подтверждает: на 166
направленных пар расхождений по счёту ноль. Разбор считается доказанным, только если из собранных
ног сходятся все семь колонок итоговой таблицы того же листа (`И В Н П Мз Мп О`) у всех
двадцати игроков — генератор падает, если не сошлись. Что говорит тема 32593813 по каждой ноге,
собирает `python collectors/season1_topic_notes.py` в `data/season1_topic_notes.json` (нужна
локальная выгрузка); генератор берёт из него только споры и пишет их в `note_leg`, чтобы человек
увидел расхождение, а не переписывал его молча (`--check` сверяет носитель с листами, повторный
прогон идемпотентен).
Сходимость проверяется до занесения: у каждой команды `сводка = ноги комментариев + выведенное`,
и если хоть одна строка не сходится, отчёт это показывает. Четыре встречи «Кометов» источник
счётов не опубликовал — их делёж по ногам следует из остатков сводки, поэтому они лежат одной
строкой без счёта (ноль вместо счёта витрина показывала бы как выдуманные голы). Две встречи
пары Den B. & Romix в теме есть, а в сводке у неё нули — по решению владельца это «ТП обоим»:
одна строка на встречу, `status = 'technical'`, исход `none` у обеих сторон, опубликованные ноги
остались в подписи и в голы не идут. И там, и там строка кладётся в очередь редактуры
(`incoming` batch `vk_live_review_41270759`) с задачей и ссылками на тему и таблицу — карточка
строки в редактуре их показывает (`db/api.locate` отдаёт `links` и `review`). Приоритет по словам
владельца у комментария: если отчёт называет запасного («E_not & Буц», комментарий 22423), ноги
пишутся на эту пару игроков, а очки пары считает сводка. Список сверки с ссылками на комментарии —
`data/youth2_group_review.md` (`python scratch/youth_groups.py`), машинная версия —
`data/youth2_group_report.json`.

Ячейка счёта в этих строках живёт текстом: «2:2 (РК 3:4)» — это ничья по голам и поражение
одной стороны по серии. Поэтому `db/import_stores.py` умеет принимать исход от вызывающего
(`outcomes=`), `matches.phase` для таких ног стоит `penalties`, а `portal/player_records.py` и
`portal/season_pages.py` читают счёт только из начала ячейки и никогда — из скобки серии или
из надписи «счёт не опубликован».

Турниры по пенальти разбираются тем же путём (`portal/penalty_sources.py`), но у каждого издания
свой носитель структуры: у 3-го (тема 33437511, апрель-май 2016) плей-офф живёт в гугл-листе
«Goal 3 PK.xls», сохранившемся как `special_tournaments/penalty3.csv`, а группы — только в
комментариях, потому что таблица групп на Диске не дожила (ссылка из первого сообщения отдаёт
404); у 4-го (тема 34920573, март 2017) сетка Full Double Elimination жива на Challonge, и её
выгрузка лежит в `data/challonge_penalty4.json` — страница закрыта Cloudflare для `curl`, но
отдаётся браузером, а данные лежат в `window._initialStoreState['TournamentStore']`. Встреча
3-го турнира, которую рамка документа описывает сама (та же пара и тот же счёт), в живые строки
не повторяется: разбор сверяет сетку с рамкой и расхождение показывает — сейчас оно одно,
суперфинал PacnyTHuK — Kunio 7:4, счёта в сетке источника нет. Нога, совпавшая со встречей сетки,
становится её доказательством: у строки появляются ссылка на комментарий и видео. Название
прикреплённого видео — тоже источник: в 48 названиях из 59 (3-й турнир) и 21 из 23 (4-й) подписаны
обе стороны, счёта там нет ни разу, поэтому из названия берутся пары, когда в тексте остался один
«5-1». Если пара названа, а счёта нет нигде, строка всё равно получает запись, а счёт — из сетки, и
это подписано в отчёте (две такие встречи). Остальное — игры группового тура; вторая нога той же пары с тем же счётом в базу не идёт (источник пишет
«0:5 0:5» как дома и в гостях, а «2:0 (5:0, 5:0)» — как две серии одной встречи, и различить их
нельзя), и каждая такая нога перечислена в отчёте с ссылкой на пост. Суперфинал 3-го турнира источник счётом не записал (в
гугл-листе пусты обе ячейки), и рукописные 7:4 из рамки убраны: строка лежит без счёта, без голов
и с задачей в редактуру — по решению владельца её правит человек в интерфейсе («для
ретроспективы»). Все 41 встреча 4-го турнира имеют след в теме. 2-й турнир (июль 2015) в теме результатов не имеет вовсе: они
выложены картинкой, и её 12 строк сверены с ней вручную. Полная сверка — `data/penalty_review.md`
(`python scratch/penalty_review.py`), машинная версия — `data/penalty_report.json`.

Сырьё раскладывается в `data/vk_dump_<дата>/`, каждый этап пропускает уже скачанное, поэтому
обход можно обрывать и продолжать. Отчёт — `data/vk_recheck_<дата>.md` для чтения и `.json` с
полем `kind` для машинного разбора; **в базу он не пишет ничего**, правки после решения владельца
идут через `db/api.py`.

Что измерено с ключом пользователя (замерено, а не по докам): `board.*`, `groups.*`, `users.get`,
`wall.search`, `docs.get` работают; `pages.get` и `pages.getTitles` отвечают кодом 3 — через API
вики этим ключом не читается; `wall.get` при паузе меньше ~2.5 с уходит в код 9 «Flood control»
и отлеживает несколько минут. Секреты читаются из `.env` (`portal/env_file.py`), в git не
попадают и наружу не печатаются.

## 🎵 Добавление музыки в аудиоплеер

Аудиоплеер автоматически подхватывает новые MP3-файлы:

1. Положите ваши `.mp3` треки в соответствующие папки внутри директории `audio/`:
   * `audio/hub/` — музыка для главного экрана (8-bit intro, темы заставки Famicom).
   * `audio/soccer/` — саундтреки Goal 3 (матчи, меню, пенальти).
   * `audio/quotes/` — атмосферная музыка для цитатника.
   * `audio/hockey/` — саундтреки Nekketsu Hockey.
   * `audio/basketball/` — саундтреки Nekketsu Street Basketball.
   * `audio/fighting/` — саундтреки Kakutou Densetsu.
2. Запустите скрипт обновления манифеста:
   ```bash
   python scan_audio.py
   ```
   *(или запустите `build.bat`)*.
3. Манифесты `audio/playlist.json` и `audio/playlist-manifest.js` обновятся автоматически, и треки появятся в плеере на сайте!

## 📊 Математика рейтингов (Elo & Dominator Score)

Формула живёт в одном месте — `portal/elo.py`; мастер-таблица больше не считает Elo сама, а
зовёт движок. Проход один, партии идут в хронологическом порядке, потому что Elo от порядка
зависит.

* **Ожидание:** `E1 = 1 / (1 + 10 ** ((R2 − R1) / 400))` — классика FIDE, шкала 400.
* **Фактический результат:** победа `1`, поражение `0`, ничья `0.5`; победа в овертайме или по
  буллитам `0.75` против `0.25` — золотой гол стоит меньше регуляторного, и это решение источника,
  а не округление.
* **Старт:** `1500` для всех. Прежде новичок получал 1600/1350/1050 в зависимости от вывески лиги
  из справочника `portal/master_tables.py`, из-за чего полтаблицы определялось классификацией,
  а не партиями. Теперь рейтинг зарабатывается играми.
* **Коэффициент:** `K = K[вес] × (1.5, пока у кого-то из пары меньше 15 партий) × MOV`, где
  `K[плей-офф] = 32`, `K[лига] = 24`, `K[остальное] = 16`, а
  `MOV = min(1 + ln(1 + |разница мячей|), 2.0)`. Разгром входит в формулу впервые: до этого
  12:0 и 1:0 двигали рейтинг одинаково, хотя в Goal 3 это разные события. Потолок двойной —
  иначе рейтинг начинал бы гонять один матч.
* **Обновление:** `R1' = R1 + K × (S1 − E1)`, округление до 0.1.
* **Простой:** штраф `0` до полугода, `25` до полутора лет, дальше `25 + 40 × (годы − 1.5)`;
  активный рейтинг не отображается ниже `1050`.
* **Что берут в расчёт:** строки с `in_rating_pool = 1` и ровно одним игроком на сторону
  (`v_rating_pool`). Флаг ставит не только импортёр пула: партию в рейтинг берёт и редактор —
  чекбоксом в карточке, `db/edit.py set-rating` по одной игре или `rate-scope` сразу сезоном или
  турниром. Отказ звучит причиной, а не молчанием: 2×2, матч без счёта, снятый с зачёта, второй
  показ дубля и партия, для которой не из чего вывести год.
* **Провизорность:** в `power_rankings` каждой строки добавлены `rated_games` и `provisional`
  (меньше 15 рейтинговых партий) — рейтинг новичка настоящий, но шаткий, и странице есть чем это
  показать.
* **Dominator Score** (без изменений по смыслу): интегральный индекс доминирования — титулы,
  процент побед, разница мячей с весом лиги и пиковый Elo, поправленный на активность.

Замерить эффект до записи можно на копии базы: `python scratch/rating_preview.py season "Season 6"`
или `... doc penalty_tournament_4` — он ничего не меняет и печатает, сколько партий войдёт,
что будет пропущено и как сдвинется таблица.
